这一版继续提速，重点是**连接间隔**——上一版只解决了“不浪费带宽”，但带宽本来就不是瓶颈。

## 为什么之前只有十几 KB/s

上传是手表驱动的：手表发 `0x28/0x05` 说“给我 offset X 开始的 N 字节”，手机写完，手表再要下一段。
两个请求之间链路上是空闲的，而每次写入都要等下一个**连接事件**。

- 连接间隔 30ms、带响应写入 → 每个间隔只能发 1 包 ≈ 8–17 KB/s，正好是“十几 KB/s”
- 连接间隔 11.25ms、无响应写入 → 每个间隔能发好几包，快 5–10 倍

MTU 早就不是瓶颈了（GT 2e 报的是 514）。Android 上的官方 App 之所以快，是因为它在传输时调用了
`BluetoothGatt.requestConnectionPriority(CONNECTION_PRIORITY_HIGH)`，把连接间隔压到 11.25–15ms。
协议本身和 Gadgetbridge / 本项目完全一样，差别只在链路参数。

## 这一版做了什么

1. **Windows 11 上请求高吞吐连接参数。** 连接成功后调用
   `BluetoothLEDevice.RequestPreferredConnectionParameters(ThroughputOptimized)`
   （UniversalApiContract v14，微软文档明确用于固件升级等高吞吐场景），断开时释放。
   日志里会打印系统给出的间隔，例如：
   `已请求高吞吐蓝牙连接参数：间隔 11.25–15.00 ms，延迟 0 个事件，超时 5000 ms`
   旧版 Windows 没有这个 API，会记一行“保持系统默认”，不影响使用。
2. **写入窗口 8 → 16 帧**，让蓝牙栈的发送队列一直有活干。
3. **诊断信息补齐**，方便判断还剩多少空间可榨：
   - `链路: 协议 v2, 分片 1022B, 手表 MTU 514B, …`
   - `发送通道: 单帧 514B（无响应写入，窗口 16 帧，已请求高吞吐连接参数）`
   - `传输参数: 单元 200B，分块加密，单帧上限 514B`
   - `数据块: 2000B → 10 个单元 / 10 帧，平均 240B/帧（单帧上限 514B）`
   - 若 FE01 同时支持两种写入方式但快速模式没开，会提示
     `FE01 支持无响应写入；开启「快速模式」可明显提速`
4. 新增 5 项测试：连接参数格式、非 Windows 跳过、请求对象保活与释放、请求失败不影响连接、
   API 缺失时静默跳过（共 102 项）。

## 还能怎么更快

按收益从大到小，复测日志能直接判断是哪一条：

| 现象 | 说明 | 下一步 |
| --- | --- | --- |
| 没有“已请求高吞吐连接参数” | Windows 10 或手表拒绝了 | 换 Windows 11，或只能接受现状 |
| 有“带响应写入” | 每个连接事件只能发一包 | 勾选「快速模式」 |
| `平均 …B/帧` 远小于 `单帧上限` | 手表的 `unitSize` 小，包填不满 | 协议限制，不能自行合并 |
| 有“并发写入不受支持” | 适配器不接受并发 GATT 操作 | 换适配器/驱动 |
